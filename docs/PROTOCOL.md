# Відкритий протокол Deye Dashboard

Платформа приймає дані інвертора чотирма шляхами. Усі відкриті: можна підключити
власний стік Deye, прозорий логер Anenji/SRNE, надіслати готові метрики в JSON по UDP
або зібрати власний пристрій з `firmware/`.

## 1. Solarman-стік напряму (без плати)

Стік LSW-3/LSE-3 має приховану сторінку `http://<ip стіка>/config_hide.html`
(admin/admin), розділ **Internal server parameters setting**:

| Поле | Значення |
|---|---|
| Protocol | TCP-Client |
| Port | 10000 |
| Server address | 193.242.161.21 (tv.sun-hunter.men) |
| TCP time out setting | 300 |

Після Save і Restart стік підключається до сервера. Сервер шле пробний V5-запит
із серійником 0, стік відповідає кадром зі своїм серійником у заголовку, далі сервер
опитує його як звичайний Modbus-шлюз (Solarman V5, control 0x4510/0x1510) кожні
10 с діапазонами з карти моделі. У кабінеті пристрій привʼязується кодом, що
дорівнює серійнику стіка. Хмара Solarman (Server A) працює як і раніше; локальний
порт 8899 у цьому режимі стік не обслуговує.

Це **не** «Remote server / Server B»: той канал використовує push-формат хмари
Solarman і з нашим сервером не працює.

## 2. Anenji / SRNE через прозорий логер (порт 8899)

Anenji — перемаркований SRNE, тому інвертор говорить **Modbus RTU** по RS485 за
відкритою специфікацією SRNE V1.7 (9600 8N1, функція 0x03, адреса в лінії зазвичай 1,
за раз гарантовано 20 регістрів). Логер у цих інверторів — не Solarman-стік, а
прозорий мост RS485↔TCP (Hi-Flying, USR, Elfin і подібні): він не парсить нічого,
а просто переливає байти в обидва боки. Майстром у лінії стає наш сервер.

У веб-інтерфейсі логера:

| Поле | Значення |
|---|---|
| Work mode / Protocol | TCP-Client (transparent) |
| Remote server address | 193.242.161.21 (tv.sun-hunter.men) |
| Remote port | 8899 |
| Baud rate | 9600, 8N1, без паритету |

Далі `apps/api/src/anenji/`:

1. **Обгортка.** Наперед невідомо, прозорий це мост чи логер з обгорткою Solarman V5,
   тому сервер чекає 0.8 с першого слова логера і пробує читання 0x0100 (SOC) обома
   способами на адресі 1, а тоді на 2…5. Відповідь, що починається з `0xA5`, означає V5;
   будь-яка інша — голий RTU. Виняток Modbus — теж відповідь: пристрій на лінії є.
2. **Ідентичність.** У прозорому мості немає ні серійника логера, ні claim-коду, тому
   пристрій ідентифікує сам інвертор: серійник з 0x0035 (20 регістрів, ASCII у
   молодших байтах, напр. `ANJ2602260356-100132`). `device_id` = перші 12 hex від
   sha256, **claim-код = останні 10 символів серійника без дефіса** (`0356100132`).
   Без серійника сесія не пише телеметрію: інакше в пристрою немає стабільного id.
3. **Опитування.** Діапазони з карти `anenji-srne` шматками по 16 регістрів кожні 10 с,
   пауза 50 мс між запитами (RS485 не любить щільних серій). Далі той самий payload,
   що й від плати, і той самий інжест.

SRNE вередливий, і драйвер це враховує:

- на моделі з одним MPPT хвіст блоку (0x010F…0x0111) віддає виняток 0x02 — сесія
  вкорочує читання на регістр і запамʼятовує розмір, який модель приймає, а не губить
  увесь блок з батареєю;
- 0x0211 (статус пароля) у частини прошивок глухо таймаутить усередині блоку, тому
  стан 0x0210 читається окремим діапазоном;
- три таймаути підряд — лінія вважається мертвою, зʼєднання рветься, логер перепідключається.

Усе, що логер шле не у відповідь на запит, лягає в `logger_frames` з `control = 0x8899`
(не більше 20 кадрів на зʼєднання). Живі сесії видно в `GET /api/admin/anenji`:
обгортка, адреса в лінії, серійник, версія прошивки, остання помилка.

Знак струму батареї в SRNE протилежний нашому (у них «+» = заряд), тому в карті
`bat_a` має відʼємний масштаб, і далі `bat_w = bat_v * bat_a` відʼємний на заряді —
як у Deye. Потужності мережі в SRNE окремого регістра немає, вона похідна:
`grid_w = grid_v_l1 * grid_a_l1`.

## 3. Готові метрики в JSON по UDP (порт 8899/udp)

Найкоротший шлях, якщо біля інвертора вже стоїть щось, що саме вміє його читати
(ESP32, Home Assistant, власний скрипт): не треба ні карти регістрів, ні опитування —
надсилайте один UDP-пакет на `193.242.161.21:8899` раз на 10 с:

```json
{"device":"b0cbd8c7e750","ac_pow":269.0,"grid_w":0.0,"grid_v":0.0,"load_w":252.0,
 "bat_v":53.3,"bat_a":-5.6,"pv_v":0.0,"pv_a":0.0,"pv_w":0.0,"ti":22.0,"td":19.0,"bc":92}
```

| Поле | Одиниці | Наша метрика | Примітка |
|---|---|---|---|
| `device` | — | id пристрою | MAC без розділювачів (12 hex) стає id як є; будь-яке інше імʼя — через sha256 |
| `load_w` | Вт | `load_w` | фактичне споживання |
| `ac_pow` | ВА | `load_va` | повна потужність на виході інвертора |
| `grid_w`, `grid_v` | Вт, В | `grid_w`, `grid_v_l1` | нуль = мережі немає |
| `bat_v`, `bat_a` | В, А | `bat_v`, `bat_a`, `bat_w` | **знак перевертається**: у цій прошивці мінус = розряд, у нас мінус = заряд (як у Deye) |
| `pv_v`, `pv_a`, `pv_w` | В, А, Вт | `pv1_v`, `pv1_a`, `pv_w` + `pv1_w` | один стрінг |
| `ti` | °C | `temp_heatsink_c` | радіатор силової частини |
| `td` | °C | `temp_dc_c` | сонячний контролер (DC-DC) |
| `bc` | % | `bat_soc` | заряд батареї |

Усі поля крім `device` необовʼязкові, незнайомі — ігноруються (прошивка може дорости).
Пристрій реєструється сам на першому пакеті, **код привʼязки — останні 8 символів id**
(для `b0cbd8c7e750` це `D8C7E750`), видно в логах і в `GET /api/admin/udp`.

Лічильників енергії (кВт·г) у цьому форматі немає, тому віджети «за добу» і місячна
статистика лишаються порожніми, поки прошивка не почне їх шле. Додайте `pv_day_kwh`,
`load_day_kwh`, `pv_total_kwh`, `load_total_kwh` — вони підхопляться без змін на сервері.

**Про безпеку.** UDP нічим не підтверджується і легко підробляється, тому: пакет не
більше 1 КБ, суворий розбір, обмеження частоти на пристрій і привʼязка до адреси —
перший пакет закріплює IP, і чужа адреса далі не приймається, доки пристрій не замовкне
на 10 хвилин (домашній IP міняється). Це захист від випадкового, а не від цілеспрямованого
підроблення: хто знає MAC, той може підсунути метрики з того ж IP. Повноцінне рішення —
токен у пакеті; воно варте зміни прошивки, якщо пристрій стоїть не у власній мережі.

## 4. Власний пристрій (ESP8266/ESP32, відкритий скетч)

Код у `firmware/`. Пристрій сам опитує стік у локальній мережі і шле сирі
регістри на брокер. Уся інтерпретація на сервері.

### 4.1 Самореєстрація

При першому старті пристрій генерує `secret` (>= 24 символи) і 8-символьний
`claimCode` (алфавіт без 0/O/1/I) і один раз викликає:

```
POST https://tv.sun-hunter.men/api/devices/register
{ "id": "<12 hex, MAC>", "secret": "...", "claimCode": "ABCD2345", "hw": "esp8266", "fw": "0.2.2" }
-> 201 { "deviceId": "..." }   | 409 device_exists | 409 claim_code_taken (згенерувати інший)
```

Ліміт 5 запитів на хвилину з однієї адреси. Далі `id` і `secret` це логін і пароль MQTT.
Код привʼязки пристрій показує в captive-порталі і на `http://<ip пристрою>/`.

### 4.2 MQTT

Брокер `tv.sun-hunter.men:8883`, TLS (Let's Encrypt), логін `id`, пароль `secret`,
client id = `id`. ACL: пристрій пише лише у свої `devices/<id>/{telemetry,status,info}`,
читає лише `devices/<id>/{cfg,cmd}`. Повідомлення понад 4 KB відкидаються;
telemetry частіше ніж раз на 2 с ігнорується.

| Тема | Напрям | Зміст |
|---|---|---|
| `devices/<id>/status` | пристрій → | `online` / `offline` (retained; `offline` як LWT) |
| `devices/<id>/info` | пристрій → | `{"fw","hw","ip","rssi","stick_ip","stick_serial","uptime","heap"}` (retained) |
| `devices/<id>/telemetry` | пристрій → | див. нижче |
| `devices/<id>/cfg` | → пристрій | `{"ranges":[[0,22],[500,700]],"interval":10,"channel":"stable"}` (retained) |
| `devices/<id>/cmd` | → пристрій | `{"cmd":"poll"|"update"|"reboot"|"rediscover"|"portal"|"stick"|"mqtt"}` |

Telemetry:

```json
{ "seq": 12, "ts": 1789231624, "uptime": 60, "stick": 2763543833,
  "ranges": [ { "start": 0,   "regs": "0006000101043233..." },
              { "start": 500, "regs": "0002..." } ] }
```

`regs` — по 4 hex-символи на регістр, big-endian, підряд від `start`. `ts` — epoch
або 0, якщо NTP ще не синхронізувався; сервер використовує свій час прийому.
Стартові діапазони `[[0,22],[500,700]]`; після визначення моделі сервер публікує
у `cfg` діапазони цієї моделі, пристрій має їх застосувати.

### 4.3 OTA

`GET /api/firmware/latest?hw=esp8266&channel=stable` →
`{"version","url","sha256","size"}` або 404. Образ завантажується з `url`
(HTTPS). Приймаються лише образи, підписані ключем платформи (ESP8266:
`Update.installSignature`, публічний ключ у `firmware/src/fw_pubkey.h`).
Канал пристрою приходить у `cfg.channel`; перевірка раз на 6 год і за `cmd update`.

## 5. Ідентифікація і карти регістрів

Регістр 0 — тип пристрою Deye: 2 string, 3 однофазний гібрид, 4 мікро,
5 трифазний LV гібрид, 6 трифазний HV гібрид. Регістри 3–7 — серійник інвертора
(ASCII), 20–21 — номінальна потужність (0.1 W, LE-слова).

Карти в `packages/register-maps/src/maps/*.json` і в таблиці `inverter_models`:

```json
{ "id": "deye-hp3", "deviceType": 6, "pollRanges": [[0,22],[500,700]],
  "fields": [ { "key": "bat_v", "reg": 587, "scale": 0.1, "unit": "V" },
              { "key": "bat_w", "reg": 590, "signed": true, "unit": "W" },
              { "key": "pv_total_kwh", "reg": 534, "words": 2, "scale": 0.1 } ],
  "derived": [ { "key": "pv_w", "sum": ["pv1_w", "pv2_w"] } ] }
```

Наявні карти: `deye-hp3` (тип 6, трифазний HV, регістри 500–700), `deye-lp3` (тип 5,
трифазний LV SG04LP3 — ті самі регістри, але `bat_v` 0.01 V і PV у ватах) і `deye-lp1`
(тип 3, однофазний LV SUN-xK-SG0xLP1, регістри 59–113 і 150–200; регістр 79 —
частота мережі, тому 32-бітний лічильник "куплено всього" = 78 + 80, поле `hiReg`).
Ключі метрик у картах однакові (`pv_w`, `bat_soc`, `grid_w`, `load_w`, …), тож
екран і кабінет не знають про модель. Регістри 20–21 на LP1 не номінал.

**GEN-порт (вхід генератора)** у трифазних картах: `gen_v_l1..l3` (661–663),
`gen_w_l1..l3` (664–666), `gen_w` (667) і лічильники `gen_day_kwh` (536),
`gen_total_kwh` (537–538). До нього підключають мікроінвертор або генератор; ця
потужність доходить до навантаження, але НЕ проходить через CT мережі, тому баланс
трифазних Deye — `load = grid + gen + inv`, а не `load = grid + inv`. Якщо порт
вільний, усі ці регістри нулі — так екран і відрізняє станції з мікроінвертором.

**Anenji/SRNE — виняток з ідентифікації.** У SRNE немає регістра типу пристрою, як у
Deye (0x000B «machine type code» — це 3/4/5, тобто ті самі числа, що й типи Deye), тому
карту `anenji-srne` ставить сам драйвер при створенні пристрою, а не `mapForDeviceType`.
Її `deviceType` 1001 — синтетичний, щоб вибір за регістром 0 ніколи не натрапив на неї.
Адреси в карті десяткові: 0x0100 = 256 (батарея і PV), 0x0210 = 528 (стан),
0x0212 = 530 (мережа, інвертор, навантаження), 0x022A = 554 (друга фаза),
0xF02D = 61485 (лічильники енергії). 32-бітні лічильники SRNE — старшим словом
уперед, тому в полі `reg` стоїть молодше слово, а `hiReg` указує на базову адресу.
Похідні вміють не лише `sum`, а й `mul` (добуток) зі `scale`.

Нову модель додавати разом із реальним дампом у `spike/dumps` і тестом балансу
(мережа + GEN + інвертор = навантаження), див. `packages/register-maps/test`.

## 6. Solarman V5, що варто знати

- Запит: `A5 len(2,LE) 10 45 seq 00 serial(4,LE) 02 0000 00000000 00000000 00000000 <modbus rtu> sum 15`;
  seq один байт, у відповіді байт 5 повторює його, байт 6 — лічильник стіка.
- Відповідь `0x1510`: payload `02 status time(4) time(4) time(4) <modbus rtu>`; checksum —
  сума байтів між `A5` і checksum, & 0xFF.
- Стік відповідає на запит із **будь-яким** серійником, підставляючи свій, тому
  серійник можна дізнатись пробою (серійник 0, регістр 0, 1 регістр).
- Один TCP-клієнт на 8899 одночасно; шматки до 60 регістрів; після обриву стік
  кілька секунд тримає старе зʼєднання. Частина стіків не відповідає на
  UDP-discovery `WIFIKIT-214028-READ:48899` — тоді скан підмережі по 8899 + проба.

## 7. Як спробувати без реєстрації в платформі

- `spike/solarman_spike.py` — читає стік із ноутбука і зберігає дамп.
- `docker-compose.dev.yml` — локальні Postgres/Redis/Mosquitto без TLS для розробки;
  `pnpm --filter @deye/api dev`.
- На проді окремого «тестового брокера» немає: будь-який пристрій самореєструється
  на бойовому брокері і до привʼязки нікому не належить; дані видно після
  привʼязки в безкоштовному тарифі.

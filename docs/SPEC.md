# Специфікація продукту (початковий промт)

## Що будуємо

SaaS-платформа: власники кафе/закладів ставлять у себе пристрій на ESP32, який забирає дані з Solarman WiFi-стіка інвертора Deye і відправляє на наш сервер. У кабінеті клієнт збирає екран — красивий відеофон (камін, водоспад, акваріум) з накладеними віджетами інвертора та опційним онлайн-радіо — і відкриває його в браузері смарт-ТБ у залі.

Працюй як senior-інженер: спершу запропонуй структуру монорепо і план по етапах, дочекайся підтвердження, потім реалізуй етап за етапом. На кожному етапі — робочий код, міграції, тести на критичну логіку (парсер протоколу, привʼязка пристроїв, права доступу). Не вигадуй бібліотеки — перевіряй, що вони існують і підтримуються.

## Стек (можеш аргументовано запропонувати заміну)

- Бекенд: Node.js + TypeScript (Fastify або NestJS), PostgreSQL + TimescaleDB для телеметрії, Redis для last-state і кешу.
- MQTT-брокер: EMQX (ACL по клієнту, rate-limit, LWT). Бекенд підписаний на брокер і пише телеметрію в Timescale.
- Auth: Keycloak (або Supabase Auth) — не пишемо власну автентифікацію. Email+пароль, Google, magic-link. Access-token короткий, refresh у httpOnly-cookie.
- Фронт кабінету: React/Next.js. Сторінка екрана для ТБ — окремий максимально легкий бандл (vanilla або Preact), без залежності від кабінету.
- Прошивка ESP32: ESP-IDF або PlatformIO/Arduino, C++.
- Інфра: docker-compose для dev, nginx з range-запитами для роздачі відео, ffmpeg для транскодування.

## Пристрій (ESP32)

1. Перший запуск — режим точки доступу з captive-порталом: клієнт з телефона вводить WiFi. Використай перевірену бібліотеку (WiFiManager / improv), не пиши свій портал.
2. Пошук стіка Solarman у локальній мережі: UDP broadcast WIFIKIT-214028-READ на порт 48899 → відповідь містить IP, MAC, серійник. Резерв: скан підмережі по відкритому TCP 8899. Можливість вручну задати IP через портал (на випадок AP-ізоляції або іншої підмережі).
3. Ідентифікатор стіка — серійник, IP лише кеш у NVS. При 2–3 таймаутах підряд або раз на годину — повторний пошук і оновлення IP по збігу серійника.
4. Опитування стіка: протокол Solarman V5 (кадр з серійником логера, всередині Modbus RTU-запит на регістри Deye). Реалізуй парсер V5 з тестами на реальних дампах.
5. Карти регістрів Deye відрізняються (гібриди SUN-xK-SG*, мережеві, мікро, різні прошивки). Пристрій шле модель/версію; список адрес регістрів для опитування отримує з сервера. Парсинг значень — на сервері, пристрій відправляє сирі регістри.
6. Транспорт: MQTT over TLS до нашого брокера, вихідне зʼєднання (пристрої за NAT клієнтів). Логін — device_id (з MAC чипа), пароль — секрет, зашитий при виробництві. Теми: devices/{device_id}/telemetry, devices/{device_id}/status (LWT), devices/{device_id}/cmd. Кожне повідомлення з timestamp.
7. OTA з підписом образу — з першої версії. Канали stable/beta.
8. Публічний відкритий скетч: документований протокол і тестовий брокер, щоб клієнт міг прошити свій ESP32.

## Сервер і модель даних

- Організації → користувачі з ролями (owner, staff, admin) → пристрої → екрани.
- Привʼязка пристрою — claim by code: на корпусі 8-символьний код, клієнт вводить його в кабінеті, сервер привʼязує device_id до організації, якщо ще не привʼязаний. Серійник стіка — лише телеметрія, не ключ доступу. Кнопка скинути привʼязку (перепродаж).
- ACL брокера: пристрій пише тільки у свої теми. Читання даних клієнтом — лише через бекенд з перевіркою організації.
- Rate-limit по пристрою на брокері.
- Телеметрія в Timescale (retention за тарифом), останній стан у Redis. Live-дані на екран — WebSocket/SSE, без полінгу.
- Статус офлайн: за LWT і за віком останнього значення. Екран мусить явно показувати застарілість.
- Нічний режим: коли інвертор спить — показувати батарею/споживання, не нулі, як у зламаного.

## Екран для ТВ
- Публічна сторінка за довгим випадковим токеном в URL, без логіну. Токен можна перевипустити. Віддає тільки поточний стан, не історію.
- Конфіг екрана — JSON (фон, список віджетів з позиціями, радіо-URL, тема). Редактор у кабінеті, рендер на ТБ.
- Фон — відео у циклі (<video autoplay muted loop playsinline>), безшовний стик, без аудіо. Три варіанти — 1080p і 720p. Роздача з range-запитами й агресивним кешуванням. Або фото (jpg/png/webp): воркер робить jpg 1080/720 і превʼю, на ТБ — нерухомий кадр з повільним наїздом; той самий контракт `files`/`preview`, `backgrounds.kind = image`.
- Радіо — <audio> зі стрімом; врахувати заборону автозапуску звуку (перший тап / екран-заставка Натисніть для старту).
- Автоперепідключення WebSocket, кеш останнього значення, watchdog на завислий плеєр — ТБ-браузери старі й засинають.
- Ніякого Three.js на ТБ за замовчуванням; WebGL-сцени — опційно.

## Бібліотека фонів і тарифи

- Таблиця фонів: файл(и), превʼю, ліцензія, джерело, категорія. Стандартні фони — зі стоків з комерційною ліцензією або згенеровані.
- Клієнт може завантажити своє відео → черга транскодування ffmpeg у стандартний формат (1080p/720p, H.264, без аудіо).
- Freemium (переглянуто 2026-09-18): Free має весь функціонал (усі віджети, власні фони, радіо, історія за рік) на 1 екран і 1 логер плюс непомітний бренд у кутку та періодична плашка з QR. Pro — те саме на 5 екранів і 5 логерів, без бренду. Max — 50/50. Ліміти тарифу зберігаються в БД (`plans.limits`), не хардкодяться.
- YouTube як фон — не підтримуємо (реклама, логотип, заборона накладення шарів). Не реалізовувати.

## Шаринг

- Посилання екрана — тільки перегляд, перевипускається.
- Запрошення в організацію — окреме одноразове посилання з TTL, видає роль (staff за замовчуванням). Owner бачить учасників і може прибирати.
- Не змішувати: перегляд не дає прав, запрошення не показує екран.

## Етапи (пропозиція, уточни)

1. Монорепо, docker-compose (Postgres+Timescale, Redis, EMQX, Keycloak), схема БД, міграції.
2. Бекенд: auth-інтеграція, організації, claim пристроїв, MQTT-інжест, REST/WS.
3. Прошивка ESP32: портал WiFi, пошук стіка, V5-парсер, MQTT, OTA.
4. Сторінка екрана для ТБ + редактор екранів у кабінеті.
5. Бібліотека фонів, завантаження/транскодування, тарифи, брендинг.
6. Документація відкритого протоколу, тестовий брокер.
